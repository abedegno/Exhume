# Porting a matched decompilation

This page is the method for turning a byte-matched, exactly linked DOS decompilation into a native program for a modern host that behaves exactly as the original did, and the tools and reference code Exhume has for it. It was extracted from UW2Decomp, whose port of Ultima Underworld II builds for macOS, Linux and Windows (its replays verified on the first two) from the same sources that still rebuild `UW2.EXE` byte for byte, and replays eight sessions recorded in DOS with the same game state and the same video memory at every checkpoint (docs/case-study-uw2.md, "The port"). skills/port-and-verify is the working order; this page is the reference.

Everything here comes after the modding build (docs/link.md) and the readability pass (docs/readability.md): a port changes shared sources, and every such change has to pass the gate.

## One tree, two builds

The DOS build and the port are built from the same sources. The DOS build is unchanged: the gate still compiles every source with the original compiler in DOS and proves the exact link and the modding build. The port compiles the same C with a modern compiler, swaps the assembly modules for C written for the port, and links them with a platform layer.

So a change made for the port must compile to the same bytes under the original compiler. Most portability changes can: a typedef, a macro that expands to the original tokens, or a prototype that agrees with the definition costs no bytes. A change that would alter the DOS bytes goes in port-only code, never in a shared source.

| Path (UW2Decomp's, then Exhume's) | What is in it | Seen by the DOS build |
| --- | --- | --- |
| `src/<subsystem>/*.C` | the game's C, shared by both builds | yes |
| `src/<subsystem>/*.ASM` | the original assembly, DOS build only | yes |
| `src/include/hookgame.h`, `rpgame.h` | the project's bindings for portable.h's hooks and for replay.c | yes (`rpgame.h`: only the replay build) |
| `src/port/portgame.h`, `asmgame.h`, `ailgame.h` | the project's bindings for the runtime's port C | no |
| `src/port/...` | the project's own port C: the replacements for its assembly modules and DOS-only C, the translated modules, the port's main, the link stubs | no |
| runtime/include/portable.h | the types and macros both builds share; each is the original tokens under Turbo C | yes, staged beside the project's headers |
| runtime/replay/replay.c | the record and replay code, compiled by the replay DOS build and the port, never by the gate | only the replay build |
| runtime/port/ | the portability layer (compat.h, force-included into every port compile, and stand-ins for the compiler's headers), the platform layer, the emulated hardware, the sound library, the x86 machine | no |

The runtime is compiled where it is (The runtime, below). exhume.toml says where the project's parts are ([port] and [replay], docs/config.md), and `[project] exclude` keeps the port's directory out of the DOS build's sources. Port files use lower-case `.c` names, and each starts with a comment naming the module it replaces, or "replaces nothing".

## The runtime

runtime/ is the half of a port that is not the game's: the portability layer, the platform layer and its SDL3 backend, the emulated VGA, EMS memory and PIT, Borland's library, the sound library for AIL 2 games, the x86 machine, record and replay and the black box (runtime/README.md lists every file). It is a library a project builds against in place, never copied into the project, so that every port of every game takes a fix to it at once and none drifts from the others. A project points at it and writes its bindings:

- **Where it is.** Exhume's tools compile the runtime of the checkout they run from, or `[port] runtime`. A project with build scripts of its own finds the checkout the same way each time (UW2Decomp's tools/exhume.py and tools/tcc.mjs: `$EXHUME`, else `.exhume` in the project, else `~/Exhume`), names the Exhume commit it was proved with in a file of its own (UW2Decomp's tools/exhume-ref; its build warns when the checkout lacks it), and has CI check out that commit into `.exhume` (tools/templates/ci's `exhume_checkout`; examples/uw2/ci.toml has UW2's, which reads the commit from that file).
- **The DOS build** stages runtime/include/portable.h beside the project's shared headers for every compile and hashes it with the sources that include it (tools/build.py, tools/srcdeps.py: `[project] include`, then the runtime's; a project header of the same name wins). The gate then proves that the runtime's portable.h costs no byte. portable.h includes the project's `hookgame.h` first, with the original tokens of its hooks.
- **The replay DOS build and the port** compile runtime/replay/replay.c as shared C (portcfg.shared_sources), with the project's `rpgame.h`.
- **The port** compiles the game's C with runtime/port/compat.h force-included and the runtime's stand-in headers, and the port's own C from the project's `[port] dir` and runtime/port together, sorted by path; the runtime's objects are named `rt_...`, since a project file may share a name with one. The include path puts the project's directory first, so the runtime's headers find its bindings (`portgame.h`, `asmgame.h`, `ailgame.h`), then runtime/port, port/platform, port/include, port/sound and port/stubs, so the project's C names the runtime's headers as `"port.h"`, `"plat.h"`, `"x86/asmrt.h"` and `"sound/audio.h"`, and its generated stubs `"stub.h"`. `[port] optimise` names directories in either tree; `[port] runtime_exclude` leaves out parts a project does not use.
- **What stays the project's**: its bindings (runtime/README.md, "The project's side", has each macro, with UW2's as the worked example); the C the runtime calls (`port_load_exe` and `port_check_exe`, `port_game_nulls`, `asm_divfault`, the glue table, the port's main and diagnostics); and everything written from or for its game: the replacements for its assembly modules and DOS-only C, the translated modules, its mouse driver, its EMS entry points over runtime/port/mem/emm.c, and anything translated from its drivers. Exhume holds none of it (docs/third-party.md).

A fix found in one game's port goes into the runtime when it is generic, is proved there on UW2 (examples/uw2/prove-port.sh) and on the other ports built on it, and reaches each project when it moves its pinned commit. UW2's rc5 to rc9 fixes show the split: the EMS page mapped into two frame slots, the Windows stream and binary-handle fixes, recording format 4 and the black box closed with the window are the runtime's; the 3D view's frame pacing (cRender waits until 8 ticks of the game clock have passed, since the game drops the fraction of the player's move each frame and a host that draws a frame in under a tick never moves a slow walk backwards) and the far procs of the graphics library called with a far return (`asm_run_far`, else the translated `retf` returns past its C caller) are UW2's, in UW2Decomp.

## Measure, compile and link

Start by measuring. `tools/portcheck.py` compiles every game C source for the host with clang, compile only, with the portability layer and no game source edited, and sorts every diagnostic into categories (inline asm, far pointers and segments, near pointers held in integers, 64-bit `long` and pointer differences, the compiler's library internals, missing declarations, `char` parameters against old-style declarations, calls without prototypes, signedness, and so on), per file, and lists the names a link would still need, by where they come from: each assembly module, the compiler's library, the far data and DGROUP gaps the link takes from the EXE, the DOS-only C, and the port layer's own names. On UW2 the first run compiled 92 of 99 sources, with 18 errors and 233 warnings, and 308 unresolved names; that list is the port's workload.

Then make the shared C compile and link, every change proved by the gate ("Writing for both builds", below). `tools/portbuild.py` compiles the game's C and the port's own C and links them; `tools/portstubs.py` writes a link stub for every name nothing defines yet (a function that names itself and stops the port; zeroed storage of the declared size for data), one file per source of the names, so that the port links on day one and a replacement deletes its stubs a file at a time. `--check` says whether the stubs are current. `portbuild.py --debug` builds with UBSan's `-fsanitize=null`, which reports a null dereference with its file and line and goes on; `--coverage` builds with clang's source-based coverage.

On UW2 this took eight steps (errors, near pointers in integers, prototypes, explicit widths, layout check, promotion audit, null pointers, far pointers and the link), after which the port linked with 160 stub functions and 80 stub variables; Milestone 3 then booted to the title with the screens matching DOS byte for byte, and Milestones 4 and 5 replaced the stubs until the replays reached the whole game loop (docs/case-study-uw2.md, "The port").

## The portability layer

runtime/port/compat.h is force-included into every game source compiled for the host, with the stand-ins for Borland's headers (runtime/port/include: `dos.h`, `alloc.h`, `mem.h`, `io.h`, `stat.h`, `dir.h`, `conio.h`, `bios.h`) ahead of the host's, so the game sources need no `#ifdef`. It:

- defines away the memory-model keywords (`far`, `near`, `huge`, `interrupt`, `cdecl`, `pascal`);
- turns `MK_FP`, `FP_SEG` and `FP_OFF` into calls into the paragraph map (below), and maps the pseudo-registers `_AX` and the rest onto a register file the port's interrupt emulation reads and writes;
- gives Borland's values to the `open` flags and permission bits, which sources also write as numbers (Borland's `O_RDONLY` is 1 where the host's is 0);
- renames the library calls whose host versions behave differently to `bc_` names, which runtime/port/sys/borland.c gives Borland's behaviour: DOS paths and case through the platform layer, text mode (CR LF, Ctrl-Z), one-argument `mkdir`, Borland's `rand` (its own generator, `RAND_MAX` 7FFFh) and `srand` (the seed's low word), `clock` at 18.2 Hz, and `time` and `rand` under the replay harness's control;
- declares Borland's extra names (`itoa`, `strupr`, `strnicmp`, `max`, `min`, `_ctype`, which a game may read directly);
- renames the game's `main` (PORT_GAME_MAIN) so the port's own main can run it on a thread of its own, and `exit` to `bc_exit`, which runs the program's termination chain and ends through the platform layer;
- packs every struct the game declares (`#pragma pack(1)`), as Turbo C does with no `-a`, after it has included every host header, so the host's own structs keep their alignment. Port C that includes a game header includes compat.h first.

The game's translation units see only ISO C and POSIX names from the host (`-D_POSIX_C_SOURCE=200809L`, [port] defines): without it macOS's headers declare names that collide with the game's (UW2: `valloc`, a routine of VALLOC.ASM).

The project's `portgame.h` names the game's main for compat.h (`PORT_GAME_MAIN`), with the rest of its bindings (The runtime, above; runtime/README.md lists them, and UW2Decomp's src/port/portgame.h is UW2's). What is the game's own code (its divide fault handlers in `asm_divfault`, asm2c's overrides, a driver's additions such as Origin's TVFX) stays in the project's repository, never in Exhume: the examples hold names, offsets and constants as configuration, and point at the project's files for the rest (docs/third-party.md).

## Memory model and data layout

A medium-model program's `int` is 16 bits, its `long` 32, and its code far; on a 64-bit host `int` is 32 bits, `long` 64 (but 32 on Windows) and pointers 64. Each difference is a place where the port can silently compute something DOS does not.

### Integer widths and wrap

The game relies on 16-bit wrap (UW2: headings are words with 10000h to the turn, so adding two wraps for free). Two parts handle it. First, explicit widths: portable.h's `int16`, `uint16`, `int32`, `uint32` are the original types under Turbo C (so the gate proves a declaration written with them compiles the same) and exact-width on the host. `tools/widths.py` rewrites declarations by the policy: `long` everywhere becomes `int32`; struct and union fields, file-scope variables and static locals get explicit widths, since their storage is what files, saves and other modules see; the pointee of every pointer to an integer and the element of every array of them too, since that is DOS-layout data and sets the stride; `sizeof` of an integer type is explicit; scalar locals, parameters and returns stay plain `int` unless their address is passed as an `int16 *` or the audit shows they depend on the wrap; `char` never changes. On UW2 it rewrote 1,210 specifiers. Defining `int` as `short` with a macro was rejected: it breaks `long int` and the host's headers, does not stop promotion, and hides the types from the debugger.

Second, the promotion audit. C promotes a 16-bit operand to the host's 32-bit `int` before arithmetic, so a result that is compared, divided, shifted right or widened before it is stored back can differ, and a `uint16` promotes to a signed `int`, so `u - 1 > 0` is true in DOS for `u == 0` and false on the host. `tools/intaudit.py` walks clang's AST, gives each expression the type Turbo C would give it, follows each value to its first consumer, and lists every place it can leave its DOS type's range before it is truncated, by category (compare, divide, shift-right, condition, widen, index, int-store, int-arg, return). Each listed site gets a cast that gives the DOS result, proved by the gate, or is recorded; the replays catch what the audit misses. On UW2 fifteen sites in ten files needed a cast, of 1,894 listed.

`char` is signed in Turbo C; the port passes `-fsigned-char` so that every host agrees.

### Far pointers and the paragraph map

Every pointer in the port is a flat host pointer, but the sources still build far pointers from segment and offset, take them apart, and do arithmetic on segment numbers (UW2: `MK_FP(EmsBuff + 0x800, off)` for page 2 of the EMS frame, `FP_SEG(drv_mem[n]) + 1`, `movedata` with `FP_SEG` and `FP_OFF` of its arguments). runtime/port/mem/parmap.c keeps a paragraph map: a table of regions, each a block of host memory with a range of DOS paragraph numbers (the EXE's far data segments, the EMS page frame, every `farmalloc` block, video memory). `MK_FP(seg, off)` finds the region holding linear address `seg * 16 + off`; `FP_SEG` and `FP_OFF` find the region holding a host pointer and give its paragraph and offset, so segment arithmetic inside a region works as in DOS. The far heap hands out blocks at offset 4 of a paragraph, as Borland's does, and a pointer derived from a block keeps the block's segment, as Borland's far pointer arithmetic did. A pointer in no region (a near buffer passed to `movedata`) gets a temporary window based at it, logged when tracing so the idiom can be given a named macro. The common idioms are portable.h macros instead (`FAR_COPY`, `FP_OFF` for an offset comparison), which need no map lookup.

A far pointer's offset wraps at 64 KB and a host pointer does not. Where the game relies on it (UW2: the cutscene player walks a large EMS page's records past E000:FFFF), runtime/port/mem/frame.c maps the frame's 64 KB twice in a row (shared memory with `mmap` on macOS and Linux, a section viewed twice on Windows), with an inaccessible page after, so a pointer that runs on past the end wraps to the start as in DOS and one that runs further faults at once.

### Near pointers in integers

A near pointer is 16 bits in DOS, so sources pass and store them in `int`s; on the host that truncates them. Each becomes a `NEARPTR` (`intptr_t` on the host) or `UNEARPTR` where two are compared unsigned, and the channels that carry one are retyped (UW2: 33 sites, among them a callback argument family, the input handlers' argument and the render database's words, which now hold `FP_OFF` values).

### Struct layout and bitfields

Turbo C lays structs out with byte alignment and puts bitfields in 16-bit units, placing each field in the 16-bit window that starts at the byte holding the next free bit (profiles/borland-tc101/compiler.md). The port packs every struct, and with 16-bit bitfield types clang then packs bitfields the same way. `tools/layoutcheck.py` tests it: for every struct and union in the shared headers it generates one program that sets each field in turn to all ones in a zeroed record and prints which bytes changed, compiles it with Turbo C in DOS and with clang, runs both and compares. On UW2 all 38 records without pointer fields came out identical, the ten with bitfields among them, and every file record ([port.layout] file_records) is checked. A struct with pointer fields cannot keep its DOS layout; it goes between `HOST_LAYOUT_BEGIN` and `HOST_LAYOUT_END` (natural alignment on the host, so its pointers are aligned, which the macOS linker requires for pointers in initialised data), and the check fails if a source moves one as bytes. One the code lays over file data is reached through `FILE_RECORDS`, which copies the records field by field (runtime/port/sys/records.c). Structs with pointers laid over shared buffers grow on the host; code that sizes them with numbers needs `sizeof`.

All file records are little-endian, as are arm64 and x86-64: no byte swapping.

### Names, prototypes and returns

- Turbo C and TASM keep 32 characters of a name with its underscore, so a C name and an assembly label that differ after that are one symbol in DOS and two on the host: the port's C defines the full C name.
- A function the original declared without a prototype, because callers push an `int` where the definition takes a `char`, gets `OLDSTYLE((params))`; a function whose callers pass an argument it ignores takes it as an unused `int` (no bytes); function pointers of mixed types are cast where they are stored. Calling through a pointer of another type works on arm64 and x86-64 because both pass arguments in registers, but it is still undefined behaviour: list the cases.
- A function the original wrote with no return statement, whose callers use what it left in AX, gets `AX_RESULT(v)` or `AX_LAST(call)`, the value read from our own build (`tools/match.py --dis`). UW2 had five.

### What x86-64 found that arm64 did not

x86-64 aligns an array of 16 bytes or more on a 16-byte boundary; arm64 happened not to. UW2's `OpenTheBag` writes past the end of one DGROUP array into the next, as DOS does on purpose; on arm64 the two arrays sat end to end on the host and the write landed where DOS's did, on x86-64 it missed and a session went another way after a bag was opened. Overflows that depend on layout show only on some hosts: run the replays on each platform the port supports, and keep two arrays that the original treats as one as one array in the port (the DOS build unchanged, the gate proving it). Also: x86-64 raises SIGFPE for an integer divide by zero, arm64 returns 0 and goes on; the promotion audit's divide sites are where to look.

## Null pointers

A null pointer does not crash a DOS program. A medium-model near null pointer reads DS:0, which holds whatever the link put just below `_DATA` (UW2: the tail of the last overlay stub entry, which the overlay manager rewrites as it loads and unloads that overlay), then C0's null area and its copyright string; a far null pointer reads the interrupt vector table. C0 checks a checksum of DS:4..30h (stock Turbo C: from DS:0) at exit and prints "Null pointer assignment" if it changed. On the host any null dereference crashes, so each site is found and decided:

- **Writes**: the replay DOS build's dumps carry DS:0..30h, C0's checksum and the vector table at every checkpoint (`replay.py nulls` checks them, with [replay.nulls]'s forms of DS:0..3), and in js-dos replaydos.mjs reads them after the program exits.
- **Reads**: clang's static analyzer over the port build; the `NULLTRAP` and `FARNULLTRAP` marks, which a replay DOS build compiled with `-DNULLTRAP` logs to NULLTRAP.LOG when it meets one; and the UBSan build over every session.
- **Deciding**: a marked site gets the bytes DOS would read (`port_null_near` and `port_null_far`, copies the project fills with `port_game_nulls`; writes land in the copies and are logged; `FARNULLREC(p, layout)` for a far pointer to a struct with the host's layout, which reads the vector table by the struct's DOS layout); or a plain guard where nothing depends on the bytes; or, for a real bug in the original, a finding with its fix as an option, the default reproducing DOS. The faithful port never crashes on a null pointer: a site the audits missed is a bug in the port. Mark a read the original makes before its own null test, too (UW2: a melee miss read the armour's item before testing the armour for null): clang at -O2 takes the dereference as proof the pointer is not null and deletes the test after it, so such a site crashes the release build even where the debug build's test would have caught it. skills/port-and-verify, "Host hazards", has the audit as steps.

## The platform layer

runtime/port/platform/plat.h is the platform API, with no SDL in it; platform/sdl3/plat_sdl3.c is the only file that includes SDL, so another host (a web build without SDL, a libretro core) is one more backend file. The model is the PC's: the game runs on a thread of its own, as the CPU did; the backend owns the window and the event loop on the main thread (which macOS and iOS require) and calls into the port as the PC's hardware interrupted the CPU, its hooks doing only what an interrupt handler could.

- **Video.** The game never presents anything. The backend calls the `scanout` hook, which reads the emulated VGA as its CRT controller would (runtime/port/gfx/vga.c: four planes, the sequencer's map mask, the graphics controller's read map and latches, the display start, pixel panning, line compare, the DAC with 6-bit colour), and draws it scaled, integer multiples and 4:3 aspect by default. The scan-out runs at the host's refresh, at no moment in particular of the game's 70 Hz frame, so it shows the display start and the pixel panning latched at the retrace, as the CRT controller takes them; read as they stand, a new start with the old panning shows for a frame and a horizontal pan judders. A screenshot the game's thread takes at a moment it chooses reads them as they stand (`vga_scanout_now`). Screenshots compare with DOS's as indexed pictures, byte for byte. Under replay the retrace bit comes from a count of reads, not the host's clock, so waits for retrace cost nothing.
- **Pointer events, not "mouse".** Each event carries a position in the game's screen pixels, already undone from the window's scaling, its motion and its buttons; the port builds int 33h's state from them, so a touch screen drives the game the same way. A game that draws its own cursor and reads only the motion (int 33h function 0Bh) drifts from the host's pointer when fed the host's motion: the mickey scaling drops a fraction whenever the count is odd, and the game stops its cursor at the edges of its box while the host's pointer goes on. So the mouse driver makes the game's cursor follow the pointer: while the event says the position is the host pointer's (`absolute`), it reports, once per move of the host's pointer, the motion that puts the game's cursor where the host's pointer is (read the game's own cursor position, take the difference, scale it back into mickeys), and no motion while the host's pointer stays still, which leaves the game's own moves of its cursor (a keyboard warp, a set position) alone. The backend hides the host's pointer over the picture. A pointer lock option (`PlatConfig.mouse_lock`) captures the pointer on a click instead, as DOSBox does, Ctrl+F10 releasing it; captured, the events carry only motion, which goes through as mickeys in whole pixels so that none is lost to the scaling. The driver needs the game's cursor, so it is the project's (UW2: UW2Decomp's src/port/sys/mousedrv.c).
- **Keyboard.** PC set-1 scan code bytes, make and break, with the prefixes, one at a time as port 60h gave them; the port repeats a held key itself at the BIOS default, so the game's own filter of repeats sees what it saw in DOS.
- **Time.** A high-resolution counter and a precise sleep; the port's PIT thread runs the timers from them, and under replay the game reads the recorded values instead.
- **Files.** The user's copy of the game is the data root, never written; the port's home directory is laid over it, so the game sees one tree, every DOS path looked up a component at a time without case (platform/files.c). A file the game opens to change is copied into the home directory at its first write.
- **Finding the game.** A player starts the port from the Finder or Explorer with no options, so the port finds the game by itself (runtime/port/sys/gamedir.c: an environment variable, the folder used last, the current and the program's own folders, GOG's registry entries on Windows and GOG's install folders on every host, a game inside GOG's CD image copied out once), and, with a window and nothing found, asks with a message box and a folder picker (`plat_message`, `plat_choose_folder`); the folder used goes to the settings file (`port_config_set`). What marks the game's folder is the project's (`PORT_GAME_EXE` and the rest in `portgame.h`, and its `port_check_exe`).
- **Lifecycle.** Suspend, resume, quit: a phone build stops the timers and saves on suspend.
- **Audio.** A stream of 16-bit stereo samples with a callback on the audio thread, which drains the ring the sound library renders into.
- **No JIT and no self-modifying code** anywhere in the port.
- **Debugging.** A screenshot after N ms or after the K-th page flip, a hidden window, quitting after N ms or where the port stops (at a stub), tracing; runtime/port/sys/crash.c prints the game thread's call stack on a host fault, and writes out the black box's recording (Verifying a port, "The black box").

Linux and Windows need only build files once the C is 64-bit clean: on Linux, SDL3 and libmt32emu from source (`tools/setup-libs.sh`, into tools/libs, found by pkg-config) where no package has them; on Windows MSYS2's CLANG64, with the few POSIX calls given Windows forms (frame.c's double mapping, a crash handler without a call stack, one-argument `mkdir`). DOS file names on a case-sensitive host need case-blind lookups everywhere a DOS program wrote them (the platform layer for the port; tools/dosbackend.mjs for emu2's outputs, which keep the case the DOS program used).

## Sound

The game's own sound code stays shared; the port replaces what is under it: the sound library's assembly, the driver files it loads, and the sound card. The aim is that the port programs the sound hardware with the same register writes and MIDI bytes the DOS drivers did, at the same moments of the game's clock, and that every value the game reads back from a driver is DOS's.

runtime/port/sound is a reusable library for games that use Miles' Audio Interface Library 2 (many 1991 to 1994 DOS games did). `ail.c` is AIL's API in C, translated from UW2's matched AIL.ASM: `API_timer`'s DDA (one PIT programmed for the shortest period any timer needs, per timer an accumulator that fires it when it reaches its period, so the music driver's service fires on the same PIT ticks relative to the game clock as in DOS), the driver table and the calls. `AIL_register_driver` recognises which driver the game loaded by the device names in the user's own `.ADV` file and reads its description table from it, so the game's view of the driver is the file's. The drivers are C written from John Miles' public-domain AIL 2.14 source: `xmidi.c` (the XMIDI sequencer shell), `yamaha.c` (the FM drivers for the YM3812, dual YM3812 and YMF262, as YAMAHA.INC was released, without `OSI_ALE`), `mt32.c` (the MT-32 through an MPU-401: the timbre cache and the system exclusive messages) and `dmasound.c` (the digital drivers: `.VOC` blocks, the double buffer, start, stop, pause, volume and pan as each card applies them). `audio.c` is the card: Nuked OPL3 for the FM chips, libmt32emu with the user's own ROMs for the MT-32, and the Sound Blaster's DAC as a mixer channel resampled from the `.VOC` time constant's rate; at every PIT tick it renders everything up to that tick's time with the registers as they are, so a write sounds from the tick it was made in, and the output is in AIL's time whatever the host does. runtime/port/sys/pit.c is the PIT thread that gives AIL the time that passes, and the BIOS tick and the keyboard's repeat. None of the third-party code is committed (docs/third-party.md).

Origin's drivers were built with YAMAHA.INC's `OSI_ALE`, which assembles in `ALE.INC`, Origin's time-variant effects (TVFX: timbres whose frequency, levels, modulation, feedback, waveforms and priority follow command lists at 60 Hz), whose source was never released. yamaha.c has a hook at each of the three places YAMAHA.INC and XMIDI.ASM call into ALE.INC: `struct AilFmExt` in runtime/port/sound/yamaha.h, with `phase` (note_on, a timbre that is not a .BNK one: `IFDEF TV_phase`), `voice_freed` (note_off freed a voice: `IFDEF TV_switch_voice`), `serve` (after every XMIDI service: `IFDEF serve_synth`) and `state_size` (the extension's own per-slot state, allocated zeroed). The extension reads and writes YAMAHA.INC's data (`Yam`) and calls its `update_voice`, `update_priority` and `release_voice`, as ALE.INC did. A project translates its drivers' ALE.INC in its own repository, lists the file in `[sound] extensions` (portbuild.py compiles one outside the port's directory too) and names its `const struct AilFmExt` to ail.c as `AIL_FM_EXT` in its `ailgame.h` (UW2: `uw2_tvfx`, UW2Decomp's src/port/sound/tvfx.c, from DM03.ADV's code at 0530h to 0ADAh). Without one, a TVFX timbre plays nothing, exactly as YAMAHA.INC without `OSI_ALE`: yamaha.h has the details.

A game's drivers may be other builds than UW2's: assemble AIL 2.14's sources with TASM and compare with the game's `.ADV` files byte for byte to see which source each is (UW2's digital drivers are 2.14's exactly; its music drivers have an older XMIDI shell and Origin's TVFX), and correct the C where they differ.

### Replays with a sound card

With a card the game reads state that time and the card change behind its back (whether the music has ended, whether a digital buffer has played out, which channel is free, which timbres the cache holds), and runs game code from the timer interrupt. Two portable.h hooks make that deterministic: `SND_READ(drv, x)` records each such read as a stream of its own (and still evaluates `x`, so the driver sees the same calls), and `SLAVE_TIMER(f)` takes a callback the driver ran from the timer interrupt and runs it at reads of the game clock instead, as many times as the DDA would have fired it by then, a function of the clock alone. Under replay the port's PIT advances by the replayed clock, one PIT tick per tick of it, so the music driver plays the session's music in the session's time, and the port compares every value its own driver had with DOS's recorded one, counting the reads where they differ: the verify fails on any.

A digital buffer ends at any moment of a tick, and the game polls its status many times in one tick, so the replay build records, with each run of sound reads, the moment within the tick DOS made the first (format 3: the PIT's count and output latched with the read-back command, an interrupt the PIC holds, and the ticks since the clock the game last read), and the port asks its driver at that moment. Under replay a transfer ends where a recorded read shows DOS's ended, within a window of 5 ms before to 1 ms after its own end, since DOSBox's Sound Blaster ends transfers early (Verifying a port, "The DOS side"); outside a replay it ends when its samples have played, as on the card.

### Checking the drivers against the real ones

The port writes logs of every AIL call the game makes, with the data it passes, and of every register write and MIDI byte its drivers make, each with its tick. `tools/ailcheck.py AIL_LOG HW_LOG` loads the user's own `.ADV` file ([sound] drivers) into Unicorn, makes the same calls with the same data in the same order, records every byte the real driver writes to the chip's or the MPU-401's ports (answering each MPU-401 command with its acknowledgement), and compares the two streams write for write and tick for tick, and the values the calls return. `tools/replay.py drivers` runs it on every session with a card. On UW2: DM03.ADV (Sound Blaster FM) 13,608 register writes over 195 calls in `sound` and 14,041 over 270 in `soundfm`, DM05.ADV (MT-32) 25,726 MIDI bytes over 280 calls in `soundmt`, all identical; the MT-32 is checked by its MIDI stream, which needs no ROM.

## Verifying a port

The test of faithfulness is to run the same session in DOS and in the port and compare the results. Doom's demos and OpenRCT2's replays work the same way.

### What is recorded

Wall-clock input timing is not enough, because a DOS program reads its clock and its devices at points that depend on how long its code takes. So the recording is made at the program's own boundary: each value it reads from the outside world, in order. Every such read in the shared sources goes through a hook of portable.h: `GAME_TIME()` for the game clock, `KEY()`, `MOUSE()`, `MBUTTONS()`, `JOY_READ()`, `JOY_BUTTONS()`, `WALL_TIME()` and `SRAND()`, with `CHECKPOINT(n)` at named points where both builds dump the state. Under the original compiler each is the original tokens (the project defines them, as `ORIG_GAME_TIME()` and the rest: UW2Decomp's src/include/hookgame.h), so the gate proves the hooks cost nothing. Replayed in order, the same values give the same `rand` sequence and the same decisions, whatever the speed of the machine.

A replay DOS build (`tools/replay.py build`) is the modding build with every source that uses a hook compiled with `-DREPLAY` and the record and replay code linked in as one more resident module (the link's `--add`). The port compiles the same code. So a session can be recorded in DOS and replayed in DOS and in the port. runtime/replay/replay.c is the reference implementation, with the game's side in a small bindings header (UW2Decomp's src/include/rpgame.h); its comment has the recording format (version 4, runs of values per stream, with the moment within the clock tick of each read of the sound hardware and repeats of the sound runs) and the dump format.

### What is compared

At each checkpoint (a `CHECKPOINT`, every 400h ticks of the replayed clock, each key event and change of the buttons, the end) both builds write the game state to `STATE.OUT`, a section per part: the game's own (UW2: the player record, the level, the 3D frame buffer, the graphics library's data), Borland's rand seed, DS:0..30h with C0's null-pointer checksum and the interrupt vector table, the calls per stream, and in a full dump the DAC, the CRT controller and all of video memory. `tools/replay.py compare` walks two dumps checkpoint by checkpoint: a header that differs means the runs went different ways before it; within a checkpoint each section is compared byte for byte, the screen also as the CRT controller shows it.

Some bytes are the program's machinery, not its state, and are masked by config: stacks that interrupts push onto whenever they come, a word the retrace wait keeps, the junk byte after a copied string, vectors a sound driver points at its handler ([[replay.mask]], [[replay.string_junk]]). Far pointers stored in game state hold segments, which differ between DOS set-ups and the port; a SEGS section lists the far blocks' segments, and a word that names block n in each build counts as equal ([replay.segments]).

### Golden references

Replaying DOS for every test is slow, so each session gets a golden reference made from DOS once: `tools/replay.py golden` replays a session in DOS twice at once, requires the two runs to be identical and the null-pointer check to pass, and writes, per checkpoint, its header and a 64-bit BLAKE2b digest of each section taken as the comparison takes it (masks zeroed, segment words replaced by the block they name), with a PNG of the screen at each full checkpoint. No dump and no game data is committed. The golden also records the SHA-256 of the recording, its configuration, the saved games the session writes, and the replay DOS build: a changed recording makes it stale and fails; a changed replay build is flagged. `tools/replay.py verify` replays the sessions in the port alone, in parallel, and compares digests, naming the first checkpoint and section that differ and drawing DOS's screen, the port's and their difference side by side.

A session that differs from its golden after a change to the port is a bug in the change: fix the port, never the golden. Goldens are made again only when a recording or the replay DOS build changes, and go in the same commit.

### The DOS side

Recording needs real-time input, so it runs in js-dos through dos-mcp (`tools/replaydos.mjs`). A replay needs no input, so it runs in native DOSBox-X when installed: headless, the game's directory mounted from the host, the dynamic core at a fixed cycle count with turbo, so emulated time runs as fast as the host can run it, three and a half times faster than js-dos on UW2. DOSBox-X loads the program at another segment, which the segment comparison allows for; on UW2 every golden made in DOSBox-X is identical to the one made in js-dos. DOSBox-X has no memory read after the program exits, so the dumps' NULL sections (C0's checksum at every checkpoint) are the null-pointer write check there.

Lessons from UW2:

- **js-dos drops sessions.** It stops a DOS session part of the way through a batch now and then, more often with several at once; tools/dosbatch.py retries a failed batch's sources alone, and replaydos bounds every call into the emulator page.
- **dos-mcp's `fsRead` refuses to read a path twice**, even one that failed because the file was not there yet. Poll for a file by listing the directory (`fsList`), and read it once.
- **DOSBox's Sound Blaster ends a transfer early.** Its mixer pulls DMA bytes in whole milliseconds and raises the interrupt when at most 3 ms are left, and js-dos's mixer runs by the host's clock, so DOS's transfers end 0 to 3 ms early by a different amount each run (on UW2 DOS's own driver disagreed with its own recording in about 14,500 of 1.8 million reads). DOSBox-X's mixer runs on the emulated clock, so there the transfers end early by the same amounts in every run (20,528 reads of UW2's `sound` session, every time), where js-dos's change from run to run. The game reads the recorded values in either, so its state agrees; the port ends a transfer where a recorded read says DOS's ended, inside a window of 5 ms before to 1 ms after its own end.
- **Narrowing a difference.** The full checkpoints only bracket where two runs part. `UWRPCK=1` makes a periodic dump at every clock tick and `UWRPFULL=lo,hi` makes those in a clock range full ones (video memory and the rest), which finds the tick; `UWRPHOOK=lo,hi` writes a full dump (kind `hook`) at every hook call whose count is in a range, which finds the call after which a section first differs; then a checksum of the suspect area, written at points traced from the code in both builds, finds the routine. All of them work in both builds and pass through tools/replaydos.mjs ([replay] env).
- **Stack junk.** A local the original reads before setting it gets whatever the stack held, and the timer interrupts write the stack, so two DOS replays of one recording can part. Find each such local (two DOS replays that differ, then `UWRPTRACE`'s call trace for where), give it `STACK_JUNK(v)`, with v the value the matched build's code shows (`tools/match.py --dis NAME` on our own object, which has the original's instructions and our names), and record the session again with that replay build. To find the rest the sessions reach, compile the port with `-ftrivial-auto-var-init=pattern` and replay every session: one that then differs reads such a local (UW2 had two, and the sessions reach no others).

### The black box

The sessions only prove what they reach. A player reaches the rest, so the port records every player's session (runtime/port/sys/blackbox.c, wired by the project's main: runtime/README.md): its inputs to `recordings/YYYYMMDD-HHMMSS/RECORD.OUT` in the home directory, with `stage/`, the home directory's files as the session began, no state dumps, and no stop key; the newest few are kept. A host fault, the game's exit and the window's closing write out the buffered streams (the last through the project's main, after `plat_run` returns: without it a session ended by closing the window lost its last chunks, the whole MISC stream once, and its replay ended at the first read of it). The header's call count is always FFFFFFFFh: live play wraps the 32-bit count within minutes, and a replay of a crash must run on into the code that crashed, so a replay of a black box recording stops only when a stream runs out. A game that polls sound state in a loop makes a run per call (UW2's alternating reads of two digital buffers' status made 900 MB in six minutes), so recording format 4 writes a continued repeat of the last one to four sound runs as one entry. A crash report with the newest folder attached replays exactly: `tools/replay.py port recordings/S/RECORD.OUT OUT --stage recordings/S/stage`. Replaying it in DOS as well (the replay DOS build, from the same stage) shows what DOS did there; then record a session of that path and add it.

### The test tiers

`tools/test.py fast` is the gate, the port build, the routine fuzzing's quick run and every session against its golden: 20 to 30 seconds on UW2, so it runs before every push (`sh tools/install-hooks.sh PROJECT "make test"`; `git push --no-verify` or `SKIP_CHECK=1` bypasses it). `tools/test.py full` adds the UBSan build (`-fsanitize=null`) over every session, every golden made again from DOS (twice each, checked identical), the sound drivers against the real ones, the deep fuzzing and `tools/coverage.py`, which writes a page of what the sessions and the fuzzing run and the functions nothing reaches: the list to record new sessions from. [test] in exhume.toml can change either tier's steps.

### Adding a session

1. Write its steps into `[replay.steps]` (tools/replaydos.mjs's steps; `@NAME` reuses another list) and, for its own configuration file, its text into `[replay.cfgs]`.
2. Record it in DOS: `tools/replay.py record OUT --session NAME`, copy `RECORD.OUT` to the sessions directory as `NAME.rec` (and the configuration as `NAME.cfg`), and look at the screenshots it took.
3. If it starts from another session's saved game, add it to `[replay] stage_from`.
4. `tools/replay.py golden NAME`, then `tools/replay.py verify NAME`, and commit the recording and its golden together.

## The static recompiler

Most of a program's assembly modules can be rewritten in C by hand, routine by routine, from the matched assembly. Some cannot, at least not first: UW2's 3D renderer (seg004, 33 KB of hand-written 386 code) is threaded code whose handlers jump into one another through a table and read registers the previous handler left; flags cross calls; routines discard their callers' return addresses or reset SP; divide faults are part of the control flow, with handlers that resume after the faulting instruction or drop the interrupt frame and jump elsewhere; code is patched at run time (immediates, a jump condition, an `add` turned into a `sub`, whole routine bodies copied over another) or generated (SCALEBM.ASM's sprite scalers). A rewrite would have to model each of these, and the frame buffer has to match DOS's to the pixel. So such modules are translated instruction by instruction, keeping the CPU's state as the CPU kept it.

`tools/asm2c.py` reads each module's matched `.ASM` source and the bytes the gate proves it assembles to (the user's EXE at the module's place), decodes the bytes with iced-x86 and walks the two together: the source gives the labels, procs, data and comments; the bytes give each instruction's address, length and operands; the two must agree on every mnemonic. TASM's padding `nop` after a forward jump it sized for the worst case is recognised, and so are instructions the source writes as bytes. Each module becomes one C function, `asm_mod_NAME(entry)`, with a label at every instruction (code jumps into unrolled loops through tables), the source line above each translated instruction, and a flag computed only where an instruction that can see it reads it (a liveness pass over the flow graph, every exit counting as a reader). What to translate is a spec file ([asm2c] spec; UW2's 26 modules are examples/uw2/port/asm2c_spec.py). The generated files are committed beside the matched sources, and `--check` says whether they are up to date.

runtime/port/x86/asmrt.h is the machine they run on: the registers are global, so what one routine leaves in a register is there for the next; each segment register keeps the host address of its offset 0, and every access is that plus a 16-bit offset, which wraps as in DOS; the stack is the emulated one, in the memory SS:SP points at. A call pushes its return address there and runs the callee through `asm_call`, which follows the callee's jumps until a return pops what it pushed; when a routine discards return addresses or resets SP, the C calls in between unwind as far as the stack pointer says, so the stack decides, as it did in DOS. A divide that would fault goes to the project's `asm_divfault`, which runs the handler the program installed; a fault the project does not model stops the port with its address rather than guess. The project's `asmgame.h` names its code blocks and its own dispatchers (UW2Decomp's src/port/asmgame.h).

No JIT and no self-modifying code in the port (iOS refuses writable executable memory, and a JIT would hide the behaviour): the code segments are host memory holding the EXE's bytes, as data. An instruction whose immediate, displacement or jump condition another instruction patches reads it from the code block at run time, and the tool refuses an instruction with a patched byte it does not read. What the generic rules cannot express is an override, C for one instruction with its reason (in the spec, or, since it is the game's code, in the project's own file named by `[asm2c] overrides`; UW2's are in UW2Decomp's tools/asm2c.py) (UW2: `mxmul` runs whichever body `check_flat` last copied over it; `modify_axis2` adds or subtracts as its patched opcode byte says; the record decoder returns where its patched `ret` is). Generated code is interpreted, not executed: UW2's sprite scaler generators write 14 kinds of instruction, and an override runs gfx/scalebm_code.c, which interprets them. A DGROUP offset or segment stops the tool: the port's DGROUP is C objects, so each needs an override.

### One implementation per routine

For a while a routine can have two implementations, the hand-written C the game's C calls and the translation the translated code calls; a slip in one cannot show where only the other runs. Keep one of each: the hand-written C where the replays reach it (they prove it, and it is the readable one), the translation everywhere else (the instructions themselves). Coverage over the sessions (`tools/coverage.py`) says which routines they reach. The spec's HANDWRITTEN lists, per module, the ranges that are hand-written C: the tool translates the rest only, a jump or fall-through into a hand-written range leaves the module (`ASM_JMP`), and the runtime sends a call or jump there to the project's glue, which does the routine's work on the emulated registers. The module table lists every place in the ranges the translation reaches (`asm_hand_calls`), and the port checks at the first translated call that each has C. The other way round, hand-written C that needs a routine the port has only as the translation calls it with the registers the assembly's caller loaded (`asm_run_near`, `asm_run_far`). On UW2 this took about 12,000 lines of duplicated C out of the port, with all eight sessions identical before and after.

This is also the way to readable C, the start of phase 2: a routine moves from the translation to HANDWRITTEN when its C, written from the translation, replays every session identically (and is fuzzed if no session reaches it), the glue keeping the translated callers working until they move too. Go from the leaves up.

## Fuzzing single routines

The sessions test what the program reaches in them. `tools/fuzzasm.py` tests single routines on inputs no session gives them: for each target it runs the routine's own bytes from the user's EXE in Unicorn, and the port's code for the same routine (its translation, its hand-written C through the glue, or a C entry) in `tools/fuzzhost.c`, a program linked from the port's objects in place of the port's main, on the same registers and memory, and compares every register, the flags the routine's callers read, and every byte of memory it changed. The memory is the EXE's image loaded at the port's load segment, so segment values agree, with two scratch segments. A divide that faults stops both and counts as agreement; memory below the final stack pointer is not compared, since hand-written C does not push what the original pushed.

The targets are a Python file ([fuzz] targets; UW2's 35 are examples/uw2/port/fuzz_targets.py): each names the routine's segment and offset, how DOS and the port call it, a generator of inputs (random, from a printed seed, with edge values first: 0, 1, 7FFFh, 8000h, FFFFh and the routine's own boundaries), and what to compare, with each register or byte left out and why (a register no caller reads, a byte the original's self-modifying code rewrites with another encoding of the same instruction). The project's side of fuzzhost is one C file ([fuzz] host_glue): the memory regions and its C entries as call kinds. `--quick` (the default) runs a few hundred cases of each target, in 13 seconds on UW2; `--deep` fifty times as many with a new seed, in the long tier.

Add a target for every routine of a translated module that the port has as hand-written C and no session reaches, so that its C is compared with the original's bytes on every push.

Unicorn 2.1.4's `emu_start` in 16-bit mode takes a linear address, and sets IP to it minus CS's base, modulo 64 KB. Pass `CS * 16 + IP`; passing the offset alone works only while CS's base is a multiple of 64 KB.

## Writing for both builds

Each of these is the original tokens under the original compiler, so the gate proves it costs nothing (runtime/include/portable.h has each with its UW2 case):

- Declare struct fields, globals and file-scope statics with explicit widths (`int16`, `uint16`, `int32`, `uint32`), and never write `long`; a pointer to an integer points to an explicit width. Plain `int` stays for a scalar local, parameter or return value whose 16-bit wrap does not matter. `tools/widths.py` applies the policy.
- A value that carries a near pointer is a `NEARPTR`; a far pointer's offset is `FP_OFF(p)`; a far copy is `FAR_COPY(dst, src, n)`.
- Cast handlers of another type where they are registered; never leave a call without a prototype; `OLDSTYLE((params))` where callers push an `int` for a `char` parameter.
- A struct with pointer fields goes between `HOST_LAYOUT_BEGIN` and `HOST_LAYOUT_END`; one the code lays over file data is reached through `FILE_RECORDS(T, p, n, layout)`.
- A dereference that can see a null pointer in DOS is `NULLTRAP(p)` (near) or `FARNULLTRAP(p)` (far), with a comment; `FARNULLREC(p, layout)` when p points to a struct with the host's layout.
- A function the original wrote with no return statement, whose callers use what it left in AX, ends with `AX_RESULT(v)` (or `AX_LAST(call)`), the value read from our own build's code.
- Every read of the world outside the program goes through a replay hook; a read of sound driver state is `SND_READ(drv, x)`, and game code a timer interrupt runs is registered through `SLAVE_TIMER(f)`.
- A store through a far pointer into the VGA's window is `PLANAR_STORE(p, v)`; a string literal the code writes into is `WRITABLE_STR(s)`; a local array the original copies past its end on purpose is `FRAME_LEN` and `FRAME_TAIL`, and one it indexes below its start is `FRAME_INDEX`, each offset read from the original's frame in the assembly; a table the original indexes past its end or before its start, into its neighbour, is `TABLE_NEXT` or `TABLE_PREV`; two locals read as one record are `READ_PAIR` and `WRITE_PAIR`; a heap of the game's own that holds pointers keeps DOS's block sizes and tag bytes with `DOS_SIZEOF`, `HOST_TABLE`, `TAG_SLOT` and `TAG_VAL`.
- A local the original reads before setting it is declared with `STACK_JUNK(v)`.
- A file whose code is DOS-only says `port: dos-only` ([port] dos_only) in its header comment, and the port replaces it.

Read compiled behaviour (AX at a function's end, what an uninitialised local holds, how an overflow wraps) from our own build: `tools/match.py --dis NAME` shows the original's instructions with our names. The C cannot say, because it keeps the undefined behaviour to keep the bytes; the port-only macro records the answer.
