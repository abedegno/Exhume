# Go 1.8.0 (`cmd/link`, `linux/amd64`) — Linker and Binary Layout

## 1. ELF sections in a Go 1.8.0 `CGO_ENABLED=0` binary

A static `linux/amd64` binary produced by `go build -gcflags "-trimpath=/build" -ldflags "-s -w"`
contains:

- `.text`: All compiled Go and runtime assembly functions, aligned to 16-byte boundaries (`0xCC`
  `INT3` padding between functions).
- `.rodata`: Constant strings, runtime type descriptors (`runtime._type`), static `funcval`
  closures (8-byte pointers to function entries), and read-only tables.
- `.typelink`, `.itablink`: Runtime reflection and interface dispatch tables.
- `.gopclntab`: Go 1.2–1.15 pclntab (magic `0xfffffffb`, `minLC=1`, `ptrSize=8`) mapping every PC
  to its function metadata, source filename, and line number. Preserved even under `-s -w`.
- `.noptrdata`, `.data`, `.bss`, `.noptrbss`: Global variables (split by pointer-containing vs
  pointer-free for the garbage collector).

## 2. Package-level verification via a harness binary

Unlike bare-metal firmware where the linker accepts a scatter file or linker script pinning each
function to its exact original virtual address, Go 1.8's `cmd/link` lays out packages globally in
import-closure order and writes all internal references as PC-relative 32-bit displacements
(`CALL rel32`, `LEA reg, [RIP+disp32]`, `MOV ..., [RIP+disp32]`).

Therefore, matching one package at a time compiles the package under a small harness (`main`
package calling the package's exported functions so `cmd/link` retains them) and verifies **three
properties** against the target binary (`gocmp`):

1. **Exact function size and instruction stream (`gocmp cmp`):** Every instruction in `[Entry, End)`
   must match identically after normalizing:
   - intra-function jump targets to `<+0xOFFSET>`,
   - inter-function calls to `<pkg.FuncName>` (resolved via `.gopclntab`),
   - static `funcval` loads in `.rodata` to `<&pkg.FuncName>`,
   - other `.rodata`/`.data`/`.bss` RIP-relative references to `<DATA>`.
2. **Exact `.gopclntab` line table (`gocmp cmp`):** Every single instruction's `basename:line` must
   equal the target binary's `basename:line`.
3. **Zero unmasked machine-code byte differences (`gocmp raw`):** Every byte in `[Entry, End)`
   outside x86-64 PC-relative displacement fields (`inst.PCRel`) must be byte-for-byte identical
   (including opcodes, REX prefixes, ModRM/SIB bytes, stack `[RSP+disp]` offsets, immediates, and
   `0xCC` tail padding).

### What PC-relative masking can hide (and how to verify it)

Because `<DATA>` masks `.rodata` addresses when linking a standalone harness:
- **String literals and byte constants** (such as error messages, salts, format strings) are stored
  in `.rodata` and loaded by RIP-relative `LEA`. Always inspect them in the target binary with
  `gocmp -addr dis` or `gocmp str BIN ADDR LEN` and verify the exact bytes in your Go source
  (e.g. an 8-byte key-derivation salt with non-printable bytes, copied byte for byte from
  `.rodata` into a `"\x.."` string literal).
- **Global variables** in `.data`/`.bss` must have the right type and initial value so package
  `init()` matches.
- **Full-binary exact link:** Once every package and `main` of the target program are recovered
  with the exact same vendor tree and Go 1.8.0 toolchain, linking `main` produces the complete
  executable without a harness.

## 3. Auto-generated functions

`cmd/compile` and `cmd/link` emit synthetic functions visible in `.gopclntab`:
- `<pkg>.init`: Package initializer (runs imported package `init`s in file-alphabetical first-import
  order, initializes package-level globals/var expressions, then calls explicit `func init()`s).
  Its prologue/epilogue line is `<last_file_alphabetically.go>:(total_lines + 1)`. Matching
  `pkg.init` proves your import set, import order, and package-level variable initializations match.
- `type..hash.*` and `type..eq.*`: Generated equality/hashing helpers for comparable struct/array
  types. Closure environments appear as `type..hash.struct { F uintptr; pkg.var T; ... }`, which
  exposes original receiver/parameter/local variable names directly in `.gopclntab` (`goclosures.py`).
- `<pkg>.(*T).M` vs `<pkg>.T.M`: Auto-generated pointer/value method wrapper stubs (e.g. embedded
  `*os.File` methods on `uncachedFile` in `store/fs`). Go 1.8 numbers `<autogenerated>` wrappers
  sequentially (`1, 2, 3, ...`) per package at compile time, including wrappers later stripped by
  `cmd/link` dead-code elimination. Matching these confirms struct embedding, receiver types, and
  unlinked method counts (see `compiler.md` §8).
